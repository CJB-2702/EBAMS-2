# Part Demand System — the Four-Axis State Model

`PartDemand` is the hub record of this app (G3): a material need moving from request through
approval, purchasing, shipping, and physical hand-off. Everything else — the rest of this app, and
any future consumer app (Maintenance, Dispatching, a future Inventory app) — is only ever allowed to
know `PartDemand.id` (G3). This document is the single reference for how a demand's status actually
works. For how a demand links to a `PurchaseOrder` and how partial fulfillment resolves, see
[purchase_ordering_system.md](purchase_ordering_system.md).

All decisions referenced below (`D#`) are recorded in [decisions.md](decisions.md).

**Revision note (2026-08-08):** this replaces the earlier three-axis model
(`workflow_state`/`order_state`/`issue_state`). Purchasing (money authorization) and shipping
(physical logistics) were originally conflated into a single `order_state` — real purchasing and
real shipping are two separate processes that don't move in lockstep (a PO can be fully approved
and paid for while the vendor is still mid-production), so they're now split into their own axes.

---

## 1. Four independent axes, not one status field

A `PartDemand` does not have a single "status." It has **four independent dimensions**, each
tracking a different kind of progress that can move at its own pace:

| Dimension | Column | Answers |
| :--- | :--- | :--- |
| **Demand** | `demand_state` | Is this need real, and authorized? |
| **Purchasing** | `purchasing_state` | Has money been authorized to move for this demand? |
| **Shipment** | `shipment_state` | Where is the material physically, in transit? |
| **Issuance** | `issuance_state` | Has this demand's material been physically handed over? |

They are independent because real fulfillment doesn't happen in strict lockstep — a demand can be
issued from stock on hand before anything is purchased for it (D11), a PO can be fully paid for
while shipment is still in production, and a demand's approval, purchasing, shipping, and issuance
progress are tracked, gated, and reasoned about separately even though a small number of rules
connect them (§3).

This is a small, fixed, closed set (M3) — not user-configurable, not templated per organization.
An earlier direction explored making these dimensions vary per organization via a generic
process-template engine; that whole design is **deferred to tech debt**, not built — see
`docs/procurement/tech_debt/20260808 process template workflow engine.md` (D21). Every
demand in this system uses the exact same four enums below, always.

**Scope note:** this kit designs the Part Demand + Purchase Order applications only. Package
intake, physical inventory tracking, and the issuance application are a **separate, later build
kit** under Inventory. `shipment_state`'s post-vendor stages and all of `issuance_state`'s actual
transition logic are therefore defined here as an enum surface other apps can target, but their
full mechanics are deliberately left open for that later kit — see the open-items note at the end
of §2.

## 2. The four enums

### `demand_state` — is the need real, and authorized?

```
Projected → Required → Approved → Completed
Required → Rejected → (resubmission) → Required
Required → Cancelled
Approved → Cancelled   (only once every linked PO is itself Cancelled — see D10, §3)
```

- **`Projected`** — a forecasted future need, not yet real. Typically auto-generated by a
  consumer app for planned work (e.g. a maintenance template projecting the parts a future PM
  will need) before anyone has actually started the task.
- **`Required`** — the need has become real. A worker starting the task it's attached to (or a
  human directly requesting the part) moves it here from `Projected`.
- **`Approved`** — a manager/approver has confirmed the demand is legitimate. Authorizes
  `purchasing_state` to leave `null` (Gate 1, §3) — same authorization role the old
  `workflow_state.Approved` played. **In practice this is usually reached automatically, not by an
  explicit Approver action** — see the auto-promote rule under §7 Personas; the Approver's manual
  approve/reject action is comparatively rare (D44).
- **`Rejected`** — declined. Loops back to `Required` on resubmission — there is no separate
  "reopen" action and no new `PartDemand` row is created (M5). The full history lives in the
  append-only journal (§4), not in a versioning scheme.
- **`Cancelled`** — terminal. Gated the same way `workflow_state → Cancelled` was (D10): a linked
  PO must reach its own cancelled state first. Rare in practice (D44).
- **`Completed`** — a **derived, auto-triggered rollup, not an independent human decision.**
  Confirmed 2026-08-08 (D43): triggers once `purchasing_state` has progressed past `null`/`Denied`
  **and** `issuance_state` has reached `Issued` — checked on every write to either axis, whichever
  condition is satisfied second. **`shipment_state` is deliberately excluded from this rollup** —
  shipping/stocking is a decoupled background process, ideally driven by an external system feed
  updating it independently (see D16's deferred integration API — this is the concrete use case
  that motivates it, even though it's still not built this kit). This matches how Requesters
  actually work the queue: marking material received is treated as "done," full stop, regardless of
  where the shipment-tracking axis happens to sit.

`Rejected` and `Cancelled` are confirmed (2026-08-08) to carry forward unchanged from the old
`workflow_state` — the earlier open item on this point is resolved.

### `purchasing_state` — has money been authorized to move?

```
null → Approved → Purchased
null → Denied
Purchased → Cancelled
```

A tracker for whether and how money starts moving for this demand — deliberately decoupled from
`shipment_state`, since a PO can be fully approved and paid for while the vendor hasn't shipped
anything yet.

- **`null`** — default. No purchasing decision has been made yet.
- **`Approved`** — a Buyer (or whoever holds the purchasing-authorization permission) has cleared
  this demand to be purchased. Distinct from `demand_state.Approved`, which authorizes purchasing
  to *begin*, not the purchase itself — a business may add more steps between the two later (per
  your "potentially adding additional steps for a business" note); this kit keeps it to one step.
- **`Denied`** — the purchasing decision was no.
- **`Purchased`** — money has actually moved (a PO is placed against this demand).
- **`Cancelled`** — the purchase was called off after being made.

**No `Manufactured Onsite` value.** In-house fabrication isn't a distinct purchasing outcome — it's
modeled as an ordinary PO placed against an internal/self vendor, going through the same
`Approved → Purchased` path as any other purchase (D34). `purchasing_state` only answers "was money
authorized to move," not "how was this fulfilled."

### `shipment_state` — where is the material, physically, in transit?

```
Request Not Sent → Request Received by Vendor → Production in Progress →
Vendor Prepared to Ship → Shipped → Delivered to Depot →
Delivered to Local Receiving Location → In Stock

Shipped → Backordered
Shipped → Lost
```

The granular logistics chain, independent of the money question. **This kit drives it up through
`Shipped`/`Backordered`/`Lost` automatically (from `PurchaseOrder.status`, D40) and adds one
explicit Buyer close-out stage at `Delivered to Local Receiving Location`** — the same
"explicit human action, not a quantity threshold" principle the old `order_state.Received` used
(D29). **Progressing to `In Stock`, and the general receiving/put-away mechanics, belong to the
separate, later Inventory build kit** (package intake, physical inventory, issuance) — left open
here, not designed. See §1's scope note and D35/D40.

### `issuance_state` — has the material been physically handed to the requester?

```
Not Issued → Partially Issued → Issued
Issued → Issued Pending Reconciliation → Issued
```

- **`Not Issued`** — nothing handed to the requester yet.
- **`Partially Issued`** — some, but not the full expected amount, has been handed over. An active,
  non-terminal state — mirrors the old `order_state.Partially Received` idea, but for hand-off.
- **`Issued`** — the normal terminal case: the requester received their material and consumed it.
  No return expected.
- **`Issued Pending Reconciliation`** — the **active** state for material that's expected to be
  partially returned (tools, borrow-and-return stock). While in this state, `issued_qty` reflects
  the full amount currently in the requester's possession. On return, the app records the returned
  quantity and the state resolves back to `Issued` with `issued_qty` reduced to the final net
  amount actually consumed — see §5 for how that's recorded.

Like `purchasing_state`/`shipment_state`, the full mechanics of *when* something enters
`Issued Pending Reconciliation` versus goes straight to `Issued` (and who decides that) are owned
by the future issuance application — left open for that kit, per the scope note in §1.

## 3. Cross-dimension gates — the complete set

A stage in one dimension can require a specific stage in *another* dimension to hold. This kit
does **not** use a generalized rules engine for this (that direction — `StageTemplate` +
`required_dimension_states`, a runtime-interpreted gate mechanism — is deferred to tech debt, see
`docs/procurement/tech_debt/20260808 process template workflow engine.md`). Instead, a
small number of gates are hardcoded, checked at execution time by a plain guard:

1. **`purchasing_state` cannot leave `null` until `demand_state` reaches `Approved`.** (D9,
   updated for the new axis split) An unapproved demand cannot be purchased against. **In
   practice, reaching `Approved` is usually a side effect of this gate, not a precondition checked
   against a separate human decision** — see D42/§7: a Buyer linking a demand to a PO auto-promotes
   `demand_state → Approved` by default.
2. **`demand_state` cannot move to `Cancelled` while a linked PO's purchasing/shipment progress is
   still active (`purchasing_state` in `Approved`/`Purchased` with the PO not itself cancelled).**
   (D10, updated) The PO must be cancelled first; only then can the demand itself be cancelled.
   Mirrors real purchasing practice — you cancel the order before you cancel the request behind it.
3. **`issuance_state` is not gated on `purchasing_state` or `shipment_state`.** (D11) Issuing from
   stock on hand, with no PO ever cut for this specific demand, is allowed at any time.
4. **`demand_state → Completed` auto-triggers once `purchasing_state` has progressed past
   `null`/`Denied` and `issuance_state` reaches `Issued` — `shipment_state` is not part of this
   check.** (D43, confirmed 2026-08-08 — revises the earlier "all three other axes must be
   terminal" framing.) Checked on every write to `purchasing_state` or `issuance_state`; not a
   human transition. See §2's `Completed` entry for the full reasoning.

If a guard cannot determine whether a transition is legal (a malformed or ambiguous check), it
**fails open** — the transition is allowed through and flagged/logged for human review, rather than
silently blocking work (D13).

## 4. The append-only journal

Each transition on any of the four dimensions is recorded as a row in the generic, append-only
`PartDemandUpdate` table: `(dimension, stage, actor, timestamp, notes)`. The four snapshot columns
on `PartDemand` (`demand_state`, `purchasing_state`, `shipment_state`, `issuance_state`) are a live
cache refreshed alongside each journal insert — fast to query, never written to directly. `notes`
stays optional free text even for `Rejected`/`Cancelled` outcomes — no mandatory reason is enforced
(D15).

This same journal is also the natural place to reconstruct issuance/return history end-to-end
(§5) — since every issuance and every return is its own row, the journal plus the paired
`PartIssuance`-style records give a full accounting without a dedicated returns table.

## 5. Quantity summary columns

Beyond the four state enums, `PartDemand` carries three quantity columns:

| Column | Default | Meaning |
| :--- | :--- | :--- |
| `quantity_requested` | — | The requested amount (what the demand originally asked for). Named explicitly — not `quantity` — to avoid mix-ups with `purchased_qty`, `issued_qty`, and `PurchaseOrderDemandLink`'s own quantity columns (D31). |
| `purchased_qty` | `0` | Live sum of `PurchaseOrderDemandLink.quantity_allocated` across every active allocation linking this demand to a PO line — how much has actually been put on order. |
| `issued_qty` | `0` | The active/net quantity currently issued to the requester — see below. |

Both `purchased_qty` and `issued_qty` are denormalized, glanceable summaries — refreshed alongside
the writes that change them (a `PurchaseOrderDemandLink` allocation/receipt, or a `PartIssuance` record),
never written to directly by a caller. Same discipline as the state snapshot columns in §4.

**`purchased_qty` is capped against `quantity_requested` — the demand's outstanding requested
amount — but the Buyer can raise the request instead of being blocked (D28).** A new allocation
that would push `purchased_qty` above `quantity_requested` triggers an explicit choice: increase
`quantity_requested` to cover it (with a strong warning that this should only be done if the
originating task genuinely needs that much), or leave the excess unallocated on the PO line for
later. A `PurchaseOrderLine` can always carry more ordered quantity than is allocated to any one
demand (extends D14's zero-linked-demand case to partially-linked lines too).

**`issued_qty` is the net, active quantity — it is not a running total of every issuance ever
made, and it is now valid for it to be `0`.** Issuance and return are modeled as two separate,
linked `PartIssuance`-style rows against the same demand: a positive row when material goes out,
and a negative row when unused quantity comes back (`issuance_state.Issued Pending Reconciliation`,
§2). `issued_qty` is always the net of those rows — the amount actually, finally consumed — so a
demand that issued 10 and had all 10 returned nets to `issued_qty = 0` without needing a separate
"was this returned" flag. (A boolean specifically marking an issuance as returned may be added
later; deliberately not built now.) It can end up less than *or* more than `purchased_qty` (or the
original `quantity_requested`) with no validation blocking either — a work order might call for 5
gallons of oil but only need 4.5 in practice. `issuance_state` never auto-flips to `Issued` based
on comparing `issued_qty` to anything else while reconciliation is pending; whoever handles the
return explicitly closes it out. **The guiding principle throughout §2 and here: business
processes are messy, and the job of this system is to give users the tools to record what actually
happened as accurately as possible, not to dictate what must be true before a demand can be marked
done.** `purchased_qty`, `issued_qty`, and every `quantity_received` value are informational inputs
to that human judgment call, never a gate.

**Receiving stays human-only for this kit phase** — there is no automated/system-driven receipt.
A `PartIssuance` row links directly to a `PartDemand`; there is no separate direct-to-asset field
on it — if the material's context involves a specific asset, that's resolved indirectly through the
demand's own origin resolution (§6/§7-style lookup via `source_module`, below), not stored
redundantly on the issuance row.

For the full mechanics of how `purchased_qty`, `PurchaseOrderDemandLink.quantity_received`, and
`purchasing_state`/`shipment_state` interact — including the worked partial-fulfillment example —
see [purchase_ordering_system.md](purchase_ordering_system.md) §3–§4.

## 6. Origin and tracking flags

`PartDemand` carries two informational columns beyond the state/quantity model:

- **`source_module`** — which originating app/module created this demand (e.g. `Maintenance`,
  `Dispatching`, `General`). Renamed and carried forward from the legacy app's
  `part_demand_type` column. Purely a denormalized convenience for cheap filtering/display —
  detailed origin context still resolves through each consumer app's own link table (`§8`), never
  through this column.
- **`serial_number_tracking_required`** (boolean, default `False`) — flags that this demand's
  fulfillment requires serial-number-level tracking. The actual serial-tracking logic is
  implemented in the future Inventory/issuance application — this column exists now purely as an
  informational contract, because upstream demand templates (e.g. a Maintenance task template)
  often already know whether serials matter for a given part and need somewhere to declare it.

## 7. Personas & permissions (D1–D4)

| Capability | Requester | Approver | Buyer |
| :--- | :---: | :---: | :---: |
| Create a demand | C | — | — |
| View a demand | R | R | R |
| Approve / reject a demand | — | U | — |
| Create / edit a purchase order | — | U (approve-transition only) | CRU |
| Allocate a demand to a PO line | — | — | U |
| Cancel a demand | U | U | — (de-links instead) |
| View demand history / journal | R | R | R |

Approve and Buy are independent, separately-grantable Django permissions, usually co-held but not
mutually required (D2). A Buyer never cancels a demand — they remove (`de-link`) the demand's
allocation from a PO instead; cancellation is a Requester/Approver action, gated by §3 rule 2 once
a PO is in flight (D4).

`Requester` is a real persona of this app now — a user creates a demand through this app's own UI,
not only via a future consumer app (D1).

### How each persona actually works the queue (D42, D44)

- **Requester — high frequency, daily, wants the path of least effort.** Their real day-to-day job
  is closing demands out: marking material received and moving `demand_state` to `Completed`. They
  don't think in terms of the four axes — they just want to mark "got it" and be done. This is
  exactly what the auto-complete rollup (§2/§3 rule 4, D43) is built for: a Requester marking
  issuance `Issued` is enough to auto-complete the demand once purchasing has cleared, without them
  ever touching `shipment_state`.
- **Approver — nominally the first gate, but often bypassed in practice.** The formal process is
  "approve before purchasing," but real usage frequently has Purchasing acting first, directing
  work through outside channels rather than waiting on an explicit approval. The Approver's manual
  approve/reject action is comparatively **low frequency** relative to Requester/Buyer activity.
- **Buyer — high frequency, daily, updates and links POs constantly.** Because the Approver step is
  often skipped in practice, linking a demand to a PO (`PurchaseOrderDemandLink` creation) **auto-promotes
  `demand_state → Approved` by default** (D42) — the Buyer can check a box before submitting to
  leave the demand unapproved instead, if they specifically want to preserve the strict
  approve-first process for that item. Gate 1 (§3 rule 1) itself is unchanged; what changes is that
  the approval is usually reached as a side effect of the Buyer's own action, not a separate human
  step waited on.
- **Shipping/stocking updates — very high frequency, ideally machine-driven.** Package and shipment
  status changes happen constantly and, ideally, get propagated down to `shipment_state` by an
  external/automated system rather than manual entry — the concrete motivating case for the
  external integration API deferred at D16. `Partially Issued` and `Backordered` are common,
  everyday occurrences, not edge cases — treat them as normal-frequency states in any future UI.
- **Cancellations — rare, across every type** (`demand_state.Cancelled`, `purchasing_state.
  Cancelled`, `PurchaseOrder.Cancelled`). Design for correctness here, not for throughput.

## 8. Domain scoping

Every `PartDemand` requires exactly one domain assignment — mandatory, not optional, not a
percentage split between restricted/unrestricted demands (D5). Whoever generates the demand (this
app's own create form, or a future consumer app) is responsible for auto-assigning the domain that
identifies who is meant to receive the part.

---

## 9. Deletion & lifecycle (D6–D8)

- **Hard delete** is allowed only while a demand is untouched — zero related rows beyond creation
  (no PO links, no issuance, no journal activity). Once anything has happened, deletion becomes
  soft-delete/deactivation, never a hard delete (D6).
- **The delete guard checks only this app's own tables** (`PurchaseOrderDemandLink`, `PartIssuance`, the
  journal). Consumer apps (Maintenance, Dispatching, a future Inventory app) own their own join
  tables FKing to `PartDemand.id` — never the reverse — so `on_delete=PROTECT` on their side blocks
  deletion for free, with zero import of consumer-app internals (D7).
- **Cross-app UI composition** uses small HTMX fragment endpoints a consumer app exposes (e.g.
  `/inventory/part-demand-status-card/<id>`), rendered on-load — not backend coupling (D8).

## 10. What this app deliberately does not do

- No per-organization variable workflow templates — every demand uses the same four enums (§1,
  D22).
- No general rules-engine gate mechanism — just the hardcoded gates in §3 (D23).
- No `PartDemand`-side comment/document thread — the two `notes` fields (on `PartDemand` and on
  each `PartDemandUpdate` row) are considered sufficient for this kit phase (M6).
- No automated/system-driven receiving — a human always records receipt and issuance (§5).
- No dedicated "was this returned" boolean on issuance yet — returns are two linked ledger rows
  net into `issued_qty` instead (§5); a flag may be added later.
- No design of `shipment_state`'s post-vendor mechanics or `issuance_state`'s reconciliation
  workflow logic — both are enum surfaces only, owned by the future Inventory/issuance build kit
  (§1).
